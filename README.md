Мульти-арендаторская (multi-tenant) SaaS-платформа для онлайн-записи в барбершопах через Telegram.
Один процесс одновременно обслуживает **несколько независимых барбершопов (арендаторов)**, каждый
со своим Telegram-ботом, своими филиалами, персоналом, услугами и тарифом — с изоляцией данных
между арендаторами на уровне каждого запроса к базе.

**Стек:** Python 3.12 · aiogram 3 · PostgreSQL 16 · SQLAlchemy 2 (async) · Alembic · APScheduler ·
Redis (FSM) · Docker.
**Языки клиентской и админ-частей:** русский, română, English.

> Этот README описывает фактическое состояние кода. Раздел [«Известные ограничения»](#известные-ограничения-и-что-не-реализовано)
> в конце явно перечисляет, чего в проекте намеренно или пока нет — не додумывайте функциональность
> сверх того, что здесь написано.

## Архитектура

### Multi-tenancy и изоляция данных

Каждая бизнес-сущность (арендатор `Tenant`, филиал `Branch`, услуга `Service`, барбер `Barber`,
клиент `User`, сотрудник `StaffMember`, запись `Appointment`, подписка `Subscription`, запись
аудита `AuditLogEntry` и т.д.) несёт колонку `tenant_id`, и каждый репозиторий, обращающийся к ней,
получает `tenant_id` в конструкторе и фильтрует по нему каждый запрос — обойти изоляцию поддельным
UUID в `callback_data` нельзя, потому что чужая запись просто не найдётся в рамках репозитория
своего арендатора. Платформенные сущности (`PlatformOperator`) — единственное намеренное
исключение: они не принадлежат ни одному арендатору вообще (см. ниже).

### Bot identity → tenant resolution

Арендатор определяется не один раз при старте процесса, а заново на **каждый** входящий Telegram-апдейт,
по тому, через какого именно бота он пришёл (`app/bot/middlewares/bot_identity.py`,
`app/services/bot_identity.py`). Таблица `telegram_bot_identities` хранит связку «Telegram bot id →
арендатор»: один арендатор может иметь несколько ботов, но не наоборот. У неизвестного или
отключённого (`is_active=false`) бота апдейт молча отбрасывается — **никакого fallback на
«арендатора по умолчанию» не существует**. Привязка бота к арендатору — явное административное
действие (`python -m app.register_bot`, см. ниже), а не побочный эффект настройки токена.
Подробности и обоснование — `docs/BOT_IDENTITY_ARCHITECTURE.md`.

### Филиалы (branches)

Один арендатор может иметь несколько физических точек (`Branch`): у каждого филиала свои часовой
пояс и валюта (`Branch.timezone`/`Branch.currency` — авторитетный источник для расчёта слотов,
форматирования времени и цен; процесс-wide `TIMEZONE`/`DEFAULT_CURRENCY` в `.env` используются
только как значение по умолчанию при онбординге, а не как рабочий часовой пояс бизнес-логики),
адрес, телефон, ссылка на карту. Доступ сотрудника к филиалам ограничивается ролью (владелец/админ
видят все филиалы арендатора, остальные роли — только назначенные). Барбер и услуга по умолчанию
доступны во всех филиалах арендатора (opt-out-модель через `BranchService`/`BarberService` — см.
ниже), удаление филиала/барбера/услуги при наличии активных записей заблокировано, вместо него —
«скрыть».

### Персонал и роли (RBAC)

`StaffMember` привязан к арендатору и имеет одну из ролей (`app/database/models/staff.py`):
`tenant_owner`, `tenant_admin`, `manager`, `receptionist`, `barber`. Права (`Permission`) —
`manage_tenant`, `manage_branches`, `manage_staff`, `view_staff`, `manage_services`,
`manage_schedule`, `manage_bookings`, `manage_customers`, `view_customers`, `view_analytics`,
`manage_settings`, `manage_subscription` — заданы статической матрицей `ROLE_PERMISSIONS` в коде
(не таблицей в БД), проверяются фильтром на уровне роутера, поэтому закрывают разом все вложенные
хендлеры и кнопки. У арендатора не может быть больше одного `tenant_owner` (частичный уникальный
индекс в БД). Подробности и таблица ролей×прав — `docs/RBAC_DESIGN.md`.

**`ADMIN_ID` не является постоянным механизмом авторизации ни на уровне арендатора, ни на уровне
платформы.** Это только точка входа для *первого* платформенного оператора и для авто-назначения
первого `tenant_owner` при первом обращении к пустому (без единого сотрудника) арендатору — см.
раздел «Платформенный control plane» ниже и `docs/PLATFORM_CONTROL_PLANE.md`.

### Услуги и барберы

Услуга (`Service`) принадлежит арендатору, имеет цену, валюту (наследуется от `Tenant.currency` на
момент создания, а не от процесс-wide настройки), длительность и описание; цена фиксируется в
записи на момент бронирования, поэтому смена прайса не переписывает историю. По умолчанию любой
барбер выполняет любую услугу в любом филиале арендатора; `BarberService`/`BranchService` —
opt-out-таблицы: явная строка с `is_active=false` точечно исключает конкретного барбера из
конкретной услуги или услугу из конкретного филиала. Привязки «цена за конкретного мастера» не
существует — цена всегда одна на услугу.

### Расписание и защита от двойной записи

Слоты считаются в чистой функции (`app/services/slots.py`) с учётом рабочего графика барбера по
дням недели, длительности услуги, уже занятых интервалов, исключений (выходной день/изменённые
часы на конкретную дату — для одного барбера или для всего филиала) и текущего времени с учётом
`MIN_LEAD_MINUTES`. Защита от двойной записи — трёхуровневая:

1. клиенту показываются только уже вычисленные свободные слоты;
2. создание записи идёт под `pg_advisory_xact_lock` по барберу с повторной проверкой слота внутри
   той же транзакции;
3. в PostgreSQL стоит `EXCLUDE USING gist` — пересечение подтверждённых записей одного барбера
   невозможно физически, на уровне констрейнта, а не только логики приложения.

### Уведомления и напоминания

Напоминания создаются вместе с записью, хранятся в таблице `notifications`
(`UNIQUE(appointment_id, kind)`) и рассылаются планировщиком (APScheduler) отдельным набором задач
**на каждого арендатора** — повторная отправка невозможна даже после перезапуска процесса.
Поддерживаются напоминания за 24 и 2 часа до визита и опциональное «пора снова записаться» через
`RETURN_REMINDER_WEEKS` недель после последнего визита. При отмене/переносе неотправленные
напоминания удаляются или пересоздаются. Планировщик выбирает бота для рассылки по самой ранней
активной привязке `telegram_bot_identities` этого арендатора.

### Биллинг, тарифы и лимиты

Три тарифа, заданные данными миграции, а не хардкодом в коде (`docs/BILLING_DESIGN.md`):

| Тариф | Кому | Функции | Лимиты |
|---|---|---|---|
| `free` | новые арендаторы по умолчанию | базовая запись, напоминания | 1 филиал, 2 барбера, 3 сотрудника, 10 услуг, 100 записей/мес |
| `pro` | платный | + CSV-экспорт, аналитика | без ограничений |
| `legacy` | служебный, не предлагается новым арендаторам | + CSV-экспорт, аналитика | без ограничений — бэкфилл для арендаторов, созданных до появления биллинга |

Лимиты проверяются в момент создания/реактивации ресурса (`LimitService`, под
`pg_try_advisory_xact_lock` для защиты от гонки при параллельном создании) — обойти лимит циклом
«скрыть → создать новый → показать скрытый» нельзя, проверка одинакова для создания и реактивации.
**Никакой интеграции с платёжными системами (Stripe, PayPal и т.п.) нет** — модель подписки и её
статусы (`trialing`/`active`/`past_due`/`canceled`/`expired`) провайдер-независимые и управляются
только изнутри приложения/CLI; онлайн-оплата не реализована.

### Онбординг нового арендатора

Арендатор появляется через платформенный слой (см. ниже), но проходит через приложение сам:

1. Платформенный оператор создаёт арендатора (`Tenant`, статус `onboarding`, тариф `free`) и
   привязывает к нему существующий Telegram-бот.
2. Первое обращение владельца к этому боту при пустом списке сотрудников автоматически назначает
   его `tenant_owner` (обвязка `_handle_inactive_tenant` в `app/bot/handlers/common.py` —
   привязка, а не постоянная авторизация).
3. Диалог онбординга в самом боте проводит через создание первого филиала (название, часовой пояс,
   валюта), первой услуги, первого барбера и расписания.
4. Как только выполнены условия готовности (есть филиал, бронируемый барбер, активное расписание),
   арендатор переводится в статус `active` и полноценно обслуживает клиентов.

### Платформенный control plane

Отдельно от арендаторской модели ролей существует платформенная идентичность — `PlatformOperator`
(без `tenant_id`, отдельная роль `platform_admin`). `PlatformAuthorizationService` управляет
доступом; окно bootstrap («пока не создан ни один `PlatformOperator`, `ADMIN_ID` временно
авторизует») самозавершается в момент появления первой реальной записи. Живой `/platform` в
Telegram (список/создание/активация/приостановка арендаторов, привязка/деактивация ботов) работает
только через отдельный, специально выделенный `PLATFORM_BOT_TOKEN` — обычный арендаторский бот
не может «стать» платформенным ни при каких обстоятельствах. Если `PLATFORM_BOT_TOKEN` не задан,
живого `/platform` просто нет, но управление арендаторами и ботами по-прежнему доступно через
сервисный слой и CLI (`python -m app.bootstrap_platform_admin`, `python -m app.register_bot`).
Подробности — `docs/PLATFORM_CONTROL_PLANE.md`.

### Локализация

Клиентская **и** административная части переведены на русский, румынский и английский
(`app/bot/i18n/`) — включая меню, процесс записи, «Мои записи», услуги, контакты, FAQ,
напоминания, тексты ошибок и весь `/admin`-интерфейс. Язык резолвится по единому правилу
(`app/services/locale.py`): явное личное предпочтение (`User.language_code` для клиента,
`StaffMember.language` для сотрудника) → `Tenant.default_language` → язык по умолчанию процесса.
При первом контакте клиента его язык инициализируется из профиля Telegram, если он поддерживается,
иначе — из языка арендатора; после этого выбор хранится и больше не перезаписывается настройкой
приложения клиента. **Живой `/platform`-интерфейс платформенного control plane локализации не
имеет** (см. ограничения ниже).

## Технологический стек

- **Python 3.12**, **aiogram 3** — Telegram Bot API (long polling).
- **PostgreSQL 16**, **SQLAlchemy 2** (async, asyncpg) — модели и репозитории.
- **Alembic** — линейная цепочка миграций `0001`…`0013` (async `env.py`, отдельный синхронный
  драйвер не нужен).
- **APScheduler** — фоновые задачи планировщика, отдельный набор на каждого арендатора.
- **Redis** — хранилище состояний FSM (без него состояния теряются при перезапуске процесса).
- **Pydantic Settings** — конфигурация из `.env`/окружения.
- **Docker Compose** — `bot` + `db` + `redis`.
- **pytest**, **ruff** — тесты и линтер.

## 1. Быстрый старт в Docker

```bash
cp .env.example .env
# заполните BOT_TOKEN и ADMIN_ID
docker compose up --build
```

**Важно про `docker-entrypoint.sh`:** он безусловно выполняет `alembic upgrade head` перед
запуском бота при **каждом** старте контейнера. Это удобно для разработки (одна команда — и база
всегда на актуальной ревизии), но для боевого сервера с реальными данными это ловушка: любой
`docker compose run bot <команда>` тоже сначала прогоняет миграцию, а значит не является
read-only-действием, даже если сама `<команда>` выглядит безобидно. Для продакшен-раскатки — см.
раздел [«Продакшен-деплой»](#продакшен-деплой) и `docs/PRODUCTION_MIGRATION_RUNBOOK.md`, где это
разобрано подробно, вместе с реальным инцидентом, который произошёл именно из-за этой особенности.

Чтобы дополнительно залить демо-данные при первом старте (тариф `free`, один арендатор, 4 услуги,
2 барбера, график Пн–Сб), поставьте в `.env`:

```env
SEED_ON_START=true
```

Остановка: `docker compose down` (данные сохраняются в volume `pgdata`), полная очистка:
`docker compose down -v`.

## 2. Переменные окружения

Минимально необходимые (полный список с комментариями — в `.env.example`):

| Переменная | Пример | Описание |
|---|---|---|
| `BOT_TOKEN` | `123456:AA...` | Токен основного бота от [@BotFather](https://t.me/BotFather) |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `barber` / `barber` / `barbershop` | Учётные данные PostgreSQL для `docker-compose.yml` — задайте свои перед боевым развёртыванием |
| `ADMIN_ID` | `123456789` или через запятую | Telegram ID для *первичного* bootstrap платформенного доступа (не постоянная авторизация — см. «Платформенный control plane») |
| `TIMEZONE` | `Europe/Chisinau` | Часовой пояс по умолчанию для нового арендатора при онбординге (рабочий часовой пояс бизнес-логики — это `Branch.timezone`, не эта переменная) |
| `DEFAULT_LANGUAGE` | `ru` | Язык по умолчанию: `ru`, `ro` или `en` |
| `DEFAULT_CURRENCY` | `MDL` | Валюта по умолчанию при онбординге нового арендатора |

Необязательные: `BOT_TOKENS` (доп. боты через запятую — каждый всё равно нужно привязать к
арендатору отдельно), `PLATFORM_BOT_TOKEN` (выделенный бот `/platform`), `REDIS_URL`, `LOG_LEVEL`,
`SQL_ECHO`, `SLOT_STEP_MINUTES`, `BOOKING_HORIZON_DAYS`, `MIN_LEAD_MINUTES`,
`CANCEL_MIN_LEAD_MINUTES`, `MAX_ACTIVE_APPOINTMENTS`, `REQUIRE_PHONE`, `THROTTLE_INTERVAL`,
`THROTTLE_BURST`, `SEED_ON_START`, `SHOP_NAME`, `SHOP_ADDRESS`, `SHOP_PHONE`, `SHOP_MAPS_URL`,
`RETURN_REMINDER_WEEKS`.

Секреты хранятся только в `.env` (файл в `.gitignore`), логи маскируют токены и пароли в DSN.
`BOT_TOKEN`/`PLATFORM_BOT_TOKEN` не привязывают бота к арендатору сами по себе — привязка это
отдельное явное действие, см. ниже.

## 3. Запуск без Docker

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env      # заполните BOT_TOKEN, ADMIN_ID, POSTGRES_*
alembic upgrade head
python -m app.seed        # необязательно: демо-арендатор с услугами/барберами
python -m app.main
```

Нужен работающий PostgreSQL 16 (расширение `btree_gist` создаётся миграцией автоматически) и,
для сохранения состояний FSM между перезапусками, Redis.

## 4. Миграции

```bash
alembic upgrade head                          # применить все — сейчас голова 0013
alembic current                               # текущая ревизия
alembic revision --autogenerate -m "описание" # создать новую после правки моделей
```

`alembic downgrade` работает на диске проекта, но **не является допустимой процедурой отката
для боевой базы** — см. `docs/PRODUCTION_MIGRATION_RUNBOOK.md`. `env.py` берёт URL из настроек
приложения и работает через async-движок, отдельный синхронный драйвер не нужен.

## 5. Первый арендатор: онбординг, бот, платформенный оператор

Локально/на новом окружении, после `alembic upgrade head`:

1. Привяжите уже настроенный `BOT_TOKEN` к арендатору (арендатора для разработки можно создать
   через `python -m app.seed` или сервисный слой `TenantOnboardingService.create_tenant`):
   ```bash
   python -m app.register_bot --tenant-id <uuid>
   ```
   Команда идемпотентна для того же арендатора и откажется молча переподключить уже привязанного
   бота к другому.
2. Напишите этому боту любое сообщение владельцем — при пустом списке сотрудников арендатора он
   автоматически станет `tenant_owner`, дальше сработает диалог онбординга в самом боте.
3. Чтобы перенести `ADMIN_ID` в управляемую таблицу платформенных операторов (не обязательно для
   работы одного арендатора, но закрывает временное bootstrap-окно):
   ```bash
   python -m app.bootstrap_platform_admin
   ```
   Идемпотентно — создаёт `PlatformOperator` для каждого id из `ADMIN_ID`, если его ещё нет.
   После этого `ADMIN_ID` для платформенной авторизации больше не используется.

## Продакшен-деплой

Полная процедура раскатки на боевой базе, включая безопасный порядок «backup → сборка нового
образа → миграция → верификация → привязка бота → запуск», список STOP-условий и
restore-based стратегию отката (**не** `alembic downgrade`) — в
[`docs/PRODUCTION_MIGRATION_RUNBOOK.md`](docs/PRODUCTION_MIGRATION_RUNBOOK.md). Читайте его
целиком перед любым действием на боевом окружении — там же разобран реальный инцидент, вызванный
особенностью `docker-entrypoint.sh` (см. предупреждение в разделе 1 выше), и то, как из него
восстанавливались без потери данных.

`scripts/verify_production_migration.py` — read-only скрипт проверки состояния БД после миграции
(ревизия, ожидаемые таблицы, `EXCLUDE`-констрейнт, уникальность владельца, изоляция между
арендаторами, целостность биллинга и языковых колонок). Он не входит в Docker-образ и запускается
только с хоста — подробности в runbook.

## Безопасность и изоляция арендаторов

- **Изоляция между арендаторами** — на уровне каждого репозитория (`tenant_id` в конструкторе,
  фильтр в каждом запросе), а не только в UI; поддельный UUID в `callback_data` не даёт доступа к
  чужим данным. См. `docs/TENANT_ISOLATION_AUDIT.md`.
- **Только личные чаты** — апдейты из групп и каналов отбрасываются до обращения к базе.
- **RBAC на уровне роутера**, закрывает вложенные хендлеры и кнопки разом; пустой `ADMIN_ID` не
  делает администратором никого ни на одном уровне.
- **Экранирование HTML** для всех пользовательских строк; **CSV-экспорт** нейтрализует формулы
  (`=`, `+`, `-`, `@`).
- **Валидация ввода**: длина, диапазоны, `NaN`/`Infinity` в цене, даты только в пределах горизонта.
- **Секреты**: токены — `SecretStr`, логи маскируют токены и пароли в DSN, ни один CLI-скрипт не
  печатает токен.
- **Флуд и лимиты Telegram**: token bucket на пользователя, обрезка длинных сообщений с корректным
  закрытием HTML-тегов.
- **Таймауты БД**: `statement_timeout`, `idle_in_transaction_session_timeout`, ограниченное
  ожидание advisory-lock.

## Известные ограничения и что не реализовано

Явно, чтобы не быть додуманным:

- **Нет интеграции с платёжными системами** (Stripe, PayPal и т.п.) — переход между тарифами и
  статус подписки управляются только вручную/через сервисный слой, не через онлайн-оплату.
- **Живой `/platform`-интерфейс не локализован** — только клиентская часть и `/admin` переведены
  на ru/ro/en; платформенная админка — фиксированный язык интерфейса.
- **Привязка нового бота через сам Telegram-чат не реализована и не планируется как временная
  мера** — токен принимается только через переменную окружения и CLI (`register_bot`), это
  осознанное решение по безопасности, а не недоделка.
- **Нет отдельной привязки цены к паре «услуга + барбер»** — цена всегда одна на услугу; opt-out
  через `BarberService`/`BranchService` определяет только доступность, не цену.
- **Один слот — один клиент**: параллельных кресел у одного барбера нет.
- **`TenantStatus.SUSPENDED`** переводится и снимается через платформенный сервисный слой
  (`TenantManagementService.suspend_tenant`/`activate_tenant`), но живого пользовательского
  UI-действия «приостановить арендатора» из `/platform` в этом README не гарантируется — сверяйтесь
  с `app/bot/handlers/platform/` за актуальным набором кнопок.
- **`docker-entrypoint.sh` не различает «применить миграцию» и «запустить бота»** — оба происходят
  в одном непрерывном шаге при каждом старте контейнера; для продакшен-раскатки это явно обходится
  процедурой из `docs/PRODUCTION_MIGRATION_RUNBOOK.md`, а не патчится в самом entrypoint.
- **Нагрузочные характеристики на большом объёме данных не измерялись** — все проверки количества
  SQL-запросов и таймингов в тестах сделаны на небольших наборах данных; поведение на
  по-настоящему крупном арендаторе (тысячи записей и больше) не верифицировано.
